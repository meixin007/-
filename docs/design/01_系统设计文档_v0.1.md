适用对象：个人开发者、协作开发 AI、Godot 地图工坊

> 本文是拟实施的设计，不是已实现功能清单。用户已确认的需求、仓库中核实的事实、本文建议参数和未决事项分别标注。尚未运行用户的本地游戏，也未取得其高度图、水系、城市点等实际数据；没有修改或提交 GitHub 仓库。

## 0. 决策摘要

采用“离线地理预处理 + 固定方向二维手绘表现 + 分块静态底图 + 可变城市模块 + 战略逻辑独立”的路线。

不要把高度图当作能直接变成参考画风的图片，也不要把每座山都变成随机摆放的山峰贴纸。高度图负责地形骨架；手绘风格由地表合成、山脊与坡面笔触、岸线处理和统一的素材共同完成。

世界逻辑上只有一套坐标与对象身份。制作、显示和存档并不是同一个文件：源数据可以重建生成结果，人工编辑必须保留，玩家的建设和战争状态由主游戏存档保存。

第一阶段不承诺全东亚量产。先做一个完整潼关节点和一张低细节东亚占位底图，同时验证最近景、最远景、跨块平移、城市变化和重生成保护。只有通过视觉、逻辑和性能三类验收后再扩大范围。

v0.1 采用纯二维运行时，不做真实三维地形、自由旋转、街道级作战和任意位置建筑摆放。建设先采用预留地块选择设施的方式。内部仍可为每个建筑记录位置，但大多数建筑只是街区美术，不单独承担完整游戏逻辑。

城市成长参考附图的“同址逐步增建”，不照搬其中的欧洲城堡、尖塔或水上城堡形制。

## 3. 总体架构与职责

### 3.1 三条职责链

**地理制作链**：原始 DEM 和位置资料 → 校准及历史修正 → 战略地形、水系和道路骨架。

**美术构建链**：地理骨架 + 风格规范 + 区域模板 + 素材包 → 默认内容 → 人工合并与校验 → 静态缓存与节点包。

**游戏运行链**：发布地图包 + 主游戏状态 → 分块加载、可变城市、军队表现和势力叠加。

不允许反向推断：隐藏一棵树不能解除禁行；废墟图片不能自行开启关隘；一条装饰船不能新增渡河边；改变相机倍率不能改变军队路线。

### 3.2 推荐模块接口

以下名称是拟新增模块，不是声称仓库已经存在。

| 模块 | 输入 | 输出与职责 |
|---|---|---|
| `LegacyMapAdapter` | 现有 v4 文档 | 保留 ID 的内部读模型及兼容报告 |
| `GeoPreprocessor` | DEM、河湖、点线面资料 | 对齐的数值地形、坡度等派生数据、质量报告 |
| `GenerationPlanner` | 地理、模板、种子、人工约束 | 不修改正式地图的候选差异集 |

| `WorldMapView` | 发布包、相机 | LOD、缓存调度、局部坐标绘制 |
| `SettlementView` | 布局、地块、游戏状态 | 当前建筑组团、损毁、扩张表现 |

## 4. 坐标、夸张和世界尺度

### 4.1 三种坐标，不混为一谈

原始资料保留其 CRS、单位和定位元数据。离线预处理统一到适合选定范围的投影坐标，保留从源到制作坐标的转换。不得把不同来源的经纬度、像素坐标直接相加。

运行时的权威位置采用“整数块索引 + 块内坐标”，或两个高精度数值分量。传给二维节点时才转换成摄像机附近的相对坐标。相机移动和渲染原点平移不改写存档中的地理坐标。

Godot 文档指出，默认 GDScript `float` 是 64 位，但默认向量分量是 32 位；大世界坐标功能也不会自动提升二维渲染精度。因此不能把巨大的绝对坐标先转换成 `Vector2`，再靠减相机位置补救。[G1]

### 4.2 固定斜俯视怎样统一

v0.1 采用一套固定地面映射和统一斜俯视素材，近远景不切换地面投影。全局视角的方向与压缩比例由小样确定一次，写入风格版本。

高度图首先驱动坡度、山脊、地表和通行约束，不直接逐像素沿屏幕竖向抬高所有对象。否则可能出现河流、道路与城池各自使用不同投影而错位。

需要真实山体遮挡时，后续可试验离线 2.5D 烘焙，但必须同时输出配准、深度或遮挡信息；不能只换地形背景，而不处理军队和建筑的显示关系。

### 4.3 城市允许夸大，但身份和连通关系不变

每个地点保存 `logical_anchor`、`display_anchor`、`visual_footprint`、`logical_connections`。近景详细布局与远景图标使用同一个显示锚点，不随缩放临时搬家。

视觉夸大不用于计算行军距离、补给成本或渡河判定。道路表现可以接向城门，但对应的逻辑边始终引用同一个地点 ID。

重要地点禁止“只放大城墙、把河堵住”的改法。周边可视走廊和不相交约束必须一起校验；无法容纳时缩减城市显示范围，而不是悄悄改动关键地理关系。

## 5. 从高度图到手绘地形

### 5.1 数值输入不能经过普通美术导入流程

保留原 DEM 数值精度、NoData、CRS、像元大小、单位和来源。坡度计算前核对水平与垂直单位。GDAL 提供重投影、坡度、坡向和晕渲等基础能力；这些是几何和分析工具，不是手绘风格生成器。[G2][G3]

Godot 的普通 PNG 导入按文档限制为每通道 8 位。不要把 16 位高度 PNG 经普通素材导入后，当作仍保留原精度的地形数据使用。建议离线处理原始地形，运行时只带必要的派生数据和美术输出；确需数值高度时使用显式定义的数据文件和读取器。[G4]

### 5.2 生成顺序

先导入并对齐资料；再叠加历史与设计修正；确认主河、水岸和重要交通走廊；推导地形类别和山脊候选；安排城市、关隘、地块及道路；生成农业和植被；最后做地表风格化及装饰合成。

重要河流优先采用已核实的矢量资料，不由 DEM 随机另生一套。河网、地形不一致时生成待处理问题，不能静默搬动河流。装饰支流也不得无意新增战略阻断。

现代资料中的人工水体、整治岸线和现代道路只作为需要核对的候选，不能默认等同唐代状态。每条历史修正记录来源、对应时代、可信度与审核状态。

### 5.3 连续地形的推荐表现

底层由地形色块、连续坡面和统一纸色构成；中层用山脊、坡脚、沟壑和岸线笔触表现起伏；上层叠加少量岩石、林簇和人工细节。

山地不是按高度阈值密铺同一座山。坡向控制笔触方向，山脊控制主线，河谷保留留白，关键走廊设置装饰禁入区。大面积底色连续，局部纹理不应每个区块单独随机归一化而露出方块边界。

v0.1 优先验证一段河岸、一面缓坡、一段陡坎和一片树林能否自然接合。若仍有明显贴纸感，暂停扩展地图数量，先改表现工艺。

## 6. 城市生成与建设

### 6.1 三种生成粒度

普通地区使用连续地表与程序装饰；一般城市使用有限原型加街区组团；重要城市与关隘使用强约束模板和人工布局。

先做两个原型族：普通平原／河岸城，以及河岸关隘。不要一开始承诺七种城市、所有建筑和全部地区风格。

### 6.2 地块优先，建筑其次

城市先定义外轮廓、城门、道路和不可建设区，再形成带稳定 ID 的地块。地块分为已建街区、可选设施地、未来扩建地与永久留白。

建议初始保留城内可开发用地的 20%–30% 给后续建设，这是待视觉小样验证的设计值。不能把河流、陡坡、主路、城门前通道和不可建设空地算进分母来凑比例。

第一版每个重点节点只设置约 6–12 个可建设地块。玩家选择地块和建筑类型，不自由拖拽任意房屋。将来扩展自由建设时再增加形状编辑、道路接入和占地碰撞规则。

### 6.3 地块最小数据

```json
{
  "id": "tongguan.slot.warehouse_01",
  "owner_site_id": "tongguan",
  "polygon_local": [[0, 0], [80, 0], [80, 60], [0, 60]],
  "allowed_buildings": ["warehouse", "granary"],
  "road_socket_id": "tongguan.road.rear_01",
  "initial_state": "empty",
  "unlock_stage": 1,
  "authoring_pin": true,
  "gameplay_buildable": true
}
```

这是拟议数据示例，不是现有插件能直接导入的文件格式。示例多边形不是实际潼关尺寸。

`authoring_pin` 禁止生成器改地块，`gameplay_buildable` 允许玩家在该地块建设，两者不能用一个 `locked` 开关混合表达。

### 6.4 扩张与损毁是两个维度

成长程度、街区占用和各模块损毁分别记录。一个成熟关隘可以严重受损，不能让“受损”自动退回“初级城市”，从而搬动剩余建筑。

布局固定，初级阶段不显示部分模块；建设解锁地块；扩张启用预先规划的外围组团；破坏替换同锚点、同占地的损毁变体。修复时恢复同一模块，不全城重新随机。

主游戏存档保存 `site_id`、`layout_version`、`growth_stage`、`slot_occupancy`、`module_damage` 和必要的毁坏种子。工坊不直接保存玩家战役进度。

## 7. LOD、缓存与画面连续性

### 7.1 四种表现，不是四张互不相关的地图

| 档位 | 内容 | 数据来源 |
|---|---|---|
| 全局 | 势力、边界、地名、海岸、主水系、概括地形 | 低分辨率地表缓存与共享逻辑矢量 |
| 区域 | 地形区、重要道路、城市剪影 | 中分辨率缓存与节点代理 |
| 地方 | 城池轮廓、周边农田、水岸和树林 | 地方底图与简化布局 |
| 近景 | 可变街区、设施、损毁、预留地块 | 细底图与可交互节点模块 |

普通地区近景可以保持概括纹理，不凭空加载同等密度的建筑。低分辨率背景始终可用，详细块未就绪时保留代理，而不是露黑块。

### 7.2 以屏幕投影尺寸切换

LOD 初始按对象显示包围盒的投影宽度决定：不足约 32 px 用图标，32–128 px 用剪影，128–384 px 用简化布局，超过约 384 px 再进入完整节点。数字是调试起点，不是性能保证。

加入约 15% 迟滞，防止临界倍率反复切换。只有目标资源就绪时才开始约 150–250 ms 的转换；最大同时显示相邻两级。

地形缓存可短时交叉淡化。建筑不要让两套不重合的黑线长时间叠加；优先让同一骨架逐步显露细节，或短时间切换代理。不能靠模糊透明度掩盖位置跳变。

文字在屏幕层绘制，暂定 14–22 个逻辑像素并适配 UI 缩放。优先保留首都、选中地点与当前行动目标，碰撞时隐藏次要名称。不要随世界比例无限缩小。

### 7.3 静态与动态分开

稳定的地表和远景普通装饰可烘焙；建设地块、成长建筑、损毁、军队、势力和文字不能烘入不可更改的全局底图。

需要遮住单位的树冠或前景城墙不能全部压入底图：保留可分层遮挡片，或规定军队只走不会产生错误交叠的展示带。建筑内部 Y 排序也不能简单代替城市与山体的遮挡设计。

现有 `art_spatial.gd` 有视觉占地和深度排序基础，可扩展资产级接地点、前后景分类、街区组团排序；仅凭图片矩形底部不一定适合复杂模块。[R5]

### 7.4 图块与资源加载

空间块、缓存纹理和行政区是三个不同概念。原型以 1024×1024 texel 缓存块为起点，另加经试验确定的边缘采样区；实际地理覆盖范围由制作比例决定。

生成时读取相邻块足够的邻域，依据对象覆盖范围决定 bleed，而不是所有素材一律加固定几像素。跨块对象有唯一所有者、其他块只引用；道路和河岸在统一世界坐标中裁切。

预加载镜头相邻一圈；限制并行读取和每帧资源挂接量；缓存按内存预算淘汰。普通 `load()` 会阻塞；使用线程加载时也必须先检查状态，过早 `load_threaded_get()` 仍可能阻塞。[G5]

后台线程主要做独占的纯数据计算和资源读取，主线程限量挂接节点。不能让工作线程任意修改活动场景树，或多线程共享修改同一资源。[G6]

### 7.5 优化选择

v0.1 首选分块底图和有限的可变节点。先量测，再决定是否为林簇引入 `MultiMeshInstance2D` 或更底层绘制。

`MultiMesh` 并非全图一开就解决性能问题：其单实例没有独立屏幕剔除，需要空间分组；二维实例也要处理透明填充和排序限制。不能用一个覆盖全东亚的 MultiMesh 装下所有树。[G7][G8]

缩放地表启用并测试 mipmap 与相应采样过滤，避免细线闪烁；仍需语义 LOD，mipmap 不负责把房屋变成城池图标。纹理合并、透明边缘扩色与过滤方式必须一起验收。[G4]

## 8. 不破坏人工编辑的重新生成

### 8.1 五类数据

| 数据 | 可否重建 | 权威来源 |
|---|---|---|
| 原始地理资料 | 原文件不可被生成器覆写 | 资料提供者 |
| 审核后的历史／设计约束 | 必须显式修改 | 地图作者 |
| 自动生成结果 | 未锁定部分可重建 | 生成器 |
| 人工覆盖与删除记录 | 不可被自动清空 | 地图作者 |
| 玩家战役状态 | 不参与制作期重生成 | 主游戏存档 |

人工“删除”也要保存；不能只存人工新增和移动。否则再次生成时被删掉的房子会回来。

### 8.2 稳定身份和局部随机

城市、河流、道路、地块使用稳定语义 ID。装饰候选使用稳定采样格和格内序号，不使用当前遍历位置。生成种子由项目种子、生成器标识、稳定地域或对象 ID 合成。

生成器及素材版本单独记录。不依赖“同一个种子在任何未来引擎版本中都天然产生同样布局”。锁定算法版本；若跨实现要求字节级一致，选定明确的伪随机算法和规范化输出。

移动一个人工对象后 ID 不变。不要把新位置写进它的身份哈希。

### 8.3 手工操作类型

支持 `add`、`update`、`delete/tombstone`、`pin` 与按区域／类别的 `exclude_generation`。锁定区域可以是多边形；锁定对象不能仅凭锚点判定，还要检查足迹、线段、阴影和笔触的覆盖范围。

生成前先把人工道路、建筑、空地与禁入区作为约束输入，生成后再合并。只在末尾叠一层人工建筑，会留下下面新长出的树林和重复建筑。

### 8.4 事务过程

1. 读取输入、旧生成结果、人工补丁、版本和内容哈希，创建只读快照。
2. 在临时区域计算选区及其依赖邻域，不直接修改当前文档。
3. 按对象身份进行旧基线、新候选和人工编辑的三方合并；受保护内容继承旧值。
4. 检查占地、地块接路、河岸连续和战略通行。
5. 对源资料与人工约束相冲突、ID 失配、锁区边界受侵入等情况生成冲突报告。
6. 展示增加、修改、删除和冲突的数量及位置，由作者确认差异。
7. 全部通过后作为一个撤销事务提交；写入新版本目录后更新发布清单指向。
8. 仅失效受影响的缓存和祖级 LOD；未修改的内容继续复用。

任一步失败时，旧地图和旧发布包继续有效。发布目录采用不可变构建编号；清单切换与重开恢复需要在目标平台实测，不能只凭内存里的状态判断成功。

### 8.5 锁区验收

分别验证对象值、规范化几何、生成身份和固定相机画面。删除记录不得丢失。为了避免边界笔触或阴影污染锁区，允许把锁区外的一圈作为需额外检查的过渡区，但不得把“过渡”当成擅自覆盖锁区的理由。

改变全局色盘、渲染器或风格版本可能改变锁区像素，必须单独申请风格迁移。局部重生成测试期间固定这些条件。

## 9. 战略逻辑与历史层

第一版推荐城市／关隘／渡口为节点，已知陆路、水路和可控通道为边，地形成本补充边的属性。现有主游戏若已有权威移动系统，应写适配器而不是同时维护第二套权威路径。

局部栅格诊断用于检查窄谷、河岸和防线，不能扩成全东亚单张高精度街道寻路网。编辑器诊断返回“当前范围没有找到路”时，不得解释为整个世界绝对无路；现有路径脚本已区分这一点。[R4]

行政地理和实时势力归属分开。历史边界只对指定剧本年份有效；未定年份时用测试区域与测试势力，不称为唐代准确疆界。

重要地点配置中记录必须保持的拓扑，例如关门所控制的道路边、是否有独立渡河路线、哪条路径仅供轻装部队通行。外观神似但能被普通军队随便绕过的关隘不合格。

## 10. 素材规范

### 10.1 资产粒度

地表色块与笔触可程序生成；林簇、岩石、街区、院落和城墙为素材组件；重要建筑保留独立对象。优先制作能组合的街区模块，不是先做几百栋独立房屋。

### 10.2 必备元数据

每件素材至少含：稳定 ID、风格版本、时代／文化标签、允许朝向、接地点、可视边界、地面占地、道路或墙体接点、排序类别、密度／尺寸范围、损毁变体组、允许的地形条件、来源说明和内容哈希。

斜俯视房屋不能靠二维随意旋转来获得正确的新朝向。墙体需要沿预设方向的成套部件。镜像同样需检查光照和结构；默认不开放随意镜像。

AI 出图必须经过透明边缘、统一线粗、比例、光向、接口、接地和组合后的检查。不要把自带天空、地面和阴影大片背景的建筑图直接放进另一个地形。

现有工坊的 PNG 导入规格有尺寸、文件大小和透明边缘限制，沿用前应按该版本导入器重新核对；源码 README 中列出的范围为边长 32–4096 像素、文件不超过 16 MiB。[R1]

### 10.3 建议生产顺序

先认可一栋房屋、一段城墙、一组树和一段坡岸的组合小样；再生产该原型所需资产；最后扩展普通城市和地区风格。风格版本更新必须保留旧包，以便锁区和存档回退。

## 11. 性能预算与测试方法

以下为建议工程目标，尚未实测，也不是对“主流配置”的事实定义。

先固定一台真实测试 PC 并记录 CPU、GPU、显存、内存、操作系统、驱动、渲染器、分辨率和构建版本。初始资源预算按 16 GB 内存、6 GB 显存的档位规划，显卡具体型号待确认。

在 1920×1080、发布构建、固定相机脚本下，暂定稳态目标 60 FPS、p95 帧时不高于 16.7 ms、p99 不高于 25 ms；地图模块驻留显存先争取在 1.5 GB 以内、进程内存约 4 GB 以内。冷加载与稳态分别统计，不以平均 FPS 遮盖卡顿。

每帧新增资源挂接预算先设为 2 ms 左右，超预算延后而不是追赶式一次加载；该值同样需要原型测量。无论性能是否达标，必须记录实际数值，不得用“感觉流畅”替代。

1024×1024 RGBA8 纹理的基础存储约为 4 MiB；完整 mip 链约 5.33 MiB。这里只是单张未压缩纹理的理论量级，不含重复副本、额外图层、缓存和运行状态。PNG 磁盘大小不能代表显存。[G4]

至少执行 60 秒来回平移和缩放、20 次节点反复进出、50 次锁区重生成、地图重开与游戏存档重读。压力样本分为真实美术场景与复制节点的纯负载场景，后者不代表历史地图已制作完成。

## 12. 开发里程碑

| 里程碑 | 交付 | 放行条件 |
|---|---|---|
| M0 基线与隔离 | 工程版本记录、只读旧样本、现有测试报告、独立工作区 | 旧文档可打开；不破坏原游戏，不写入旧素材包 |
| M1 坐标和缩放骨架 | 东亚粗占位、一个节点占位、四档显示、拾取 | 同一锚点、最远到最近可往返，无明显漂移或空白 |
| M2 视觉工艺 | 一小段坡岸、树林、道路与建筑组合 | 作者认可组合画面；不只认可单件 AI 图 |
| M3 生成与保护 | 分块候选、稳定 ID、补丁、差异预览、事务 | 改密度／种子后保护、删除与跨块边界测试通过 |
| M4 潼关节点 | 地理骨架、6–12 地块、建设及损毁 | 看起来是卡口；逻辑上控制对应通道 |
| M5 发布与压力 | 运行时包、存档适配、全尺度压力报告 | 发布构建达成约定预算或明确记录差距并缩减范围 |

M1 和 M2 需要尽早并行验证。不能把美术验证推迟到框架全部完成后，也不能用一张漂亮静态图代替结构与缩放验证。

## 13. 推荐目录与版本策略

以下为拟新增目录，落地前通过现有源码允许列表审查。美术产物放在独立工作工程或经批准的发布目录，不直接写进目前仅源码的导出包。

```text
map_pipeline/
  schemas/                 # 世界清单、生成配方、补丁格式
  preprocess/              # 地理离线预处理
  generators/              # 地形装饰、聚落、关隘
  compiler/                # 分块和节点编译
  tests/                   # 单元、集成与验收脚本
map_workspace/
  sources/                 # 原始资料，只读
  constraints/             # 历史、地理、设计约束
  authoring/               # 旧文档与人工制作文件
  overrides/               # 增改删、冻结和锁区
  art_bundles/              # 已认可、带版本素材
  builds/<build_id>/        # 不可变发布包
  reports/<build_id>/       # 回归、性能与相机证据
```

清单至少记录 `schema_version`、`world_id`、`scenario_year`、`source_hashes`、`generator_versions`、`style_version`、`asset_bundle_hash`、`layout_versions`、`build_id` 与产物哈希。存档更新布局版本时必须使用地块迁移表，不能随机重绑玩家建筑。

## 14. v0.1 完成定义

完成不是“搭好很多类”。必须有一个可运行发布构建，能从粗略东亚底图定位到潼关近景，改变关隘状态，建设一个预留地块，保存并重读；还能在工坊中重生成树林而不改掉人工道路、删掉的对象和锁定关城。

视觉、地理、可维护性与性能分别给证据。任一关键维度未通过，就明确记录为未通过，而不是用其他维度的成果替代。
