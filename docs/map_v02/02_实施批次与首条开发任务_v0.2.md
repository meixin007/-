# 唐代战略地图 v0.2｜实施批次与首条开发任务

本文件是《系统设计文档 v0.2》的执行附件，不是代码交付或验收结果。基线为 `62546a547895e1a6185904ad60bf15fa58c03244`。用户提出设计v0.2不等于已经批准任何新组合画面；作者审阅是独立关卡。

## 1. 实施顺序

先完成 **S0**，随后立即启动 **V1**。风格等待审阅期间可用旧资产／灰盒处理 **E1**；**E2、E3**须逐步验证后继续。通过风格关卡后做 **V2**，最后完成 **C1、Q1**。不在第一条任务里一次性执行全部批次。

| 批次 | 该批解决的问题 | 主要交付 | 明确不做 |
|---|---|---|---|
| S0 | 新旧版本能否可追溯对照，计时与分辨率是否可信 | 基线收据、新入口、旧逻辑复验、观测指标及测试profile | 不改存档、生成器与正式画风 |
| V1 | 组件能否拼成用户要的画面 | 风格卡、12—16件以内的小样、接点与同镜头对照 | 不生成几十种建筑，不擅改旧图 |
| E1 | 制作快照能否变成独立分页包 | 最小包协议、4×4夹具、依赖与校验、发行加载 | 不建设全国地理数据库 |
| E2 | 能否只处理镜头附近的对象 | 反向桶、修订更新、可见排序缓存、真实提交审计 | 不只是把全量循环改名为query |
| E3 | 能否真正加载和释放 | 加载状态机、预算、epoch、缺页回退、不同区域重载 | 不以隐藏节点或关界面冒充卸载 |
| V2 | 连续地形与已有玩法能否结合 | 坡岸笔触、院落、墙段、原位损毁、风格迁移收据 | 不新增经济、战斗或任意摆房 |
| C1 | 两条线是否使用同一个运行系统 | 实际潼关样板、合成多区域、标签势力最小验证 | 不为演示另建一套加载器／GameState |
| Q1 | 是否满足完成定义 | 完整验收矩阵、压力与故障数据、新发行和回退说明 | 不自动进入第二历史节点或全国量产 |

## 3. V1 的交付要求

V1不是写更多美术规范后就结束。至少在Godot里组装“坡岸＋水＋树＋道路＋墙＋关楼”，保存固定相机，显示实际参考线与接点。

最多两套候选方向，先使用可复用旧素材。新资产另存版本，不覆盖现有PNG或图集。所有方向、阴影、线粗、地面轴必须在组合中检查；独立资产很漂亮并不是通过条件。

作者审阅结果保存在 `visual_review` 记录中：具体build_id、素材清单哈希、相机名、accepted／revision_requested／rejected及文字意见。没有作者意见时是pending，不得写accepted。

风格卡确定后，E1/E2可继续使用占位资源验证接口。新的完整风格与旧锁区像素冲突时，单独提供迁移范围和可回退包。

## 4. E1 的最小协议边界

协议只保存表现包信息，不改旧v4或Save22。先给一个4×4稀疏地形夹具，至少含跨块树、穿越边界的道路／水岸、一个地点代理、一个可缺失子页和一个父级回退。

导入必须先检查原始对象列表ID，再投影为字典；保留来源ID，不能把chunk坐标编码成新的逻辑身份。平移对象跨页后对象仍是同一个对象。

文件缺失、哈希错误、schema不支持、世界／布局不兼容、越界路径应各有拒绝用例。运行包从干净目录启动，证明JSON与纹理依赖确实被导出，而不是恰好从编辑器缓存读到。

## 5. E2/E3 不能省略的反例

**E2：** 树的owner块在视口外，但树冠在视口内；超大树覆盖四块；旧ID重复；record.id与key不一致；换大素材后旧桶范围失效；只移动相机时全量plan计数不得增加；在相同可见量下增加离屏对象，查询结果保持正确。

**E3：** 快速A→B→A时A的旧请求迟到；切换包后旧纹理完成；细页缺失；旧子页与新父页版本不匹配；共享图集最后引用释放；正在淡化时预算减少；清空自有缓存后旧绘制命令仍持有纹理；数据总量远超软预算，访问多个区域后真正发生释放与重载。

错误注入必须先证明错误会被检测，不能只确认“程序没有崩溃”。缺页场景预期是细节失败且父页回退成功，不是整批资源加载成功。

## 6. V2/C1 的冻结项

不更改关门、八地块、主通道、已登记支路接点、生成器身份或存档格式来方便新美术。需要更大建筑时先调整表现尺寸或资产；无法满足时提出明确布局变更议题，不自动迁移。

不把运行中的玩家建筑烘入静态地形。城镇被卸载后，日期与施工由原服务继续管理；再次出现时读取最新状态。军队仍使用战略标记，不把门洞人物遮挡变成临时新增需求。

真实样板与合成夹具共用加载器。合成地点使用工程命名，不伪装成长安、洛阳或另一真实关隘，避免误把性能测试资产当成内容生产进度。

## 7. 每个PR的最小交付格式

说明基线与实际父提交、变更范围、受影响契约、原有用例与新增用例、执行环境、输出构建和哈希、未执行／失败事项、回退方法。不要只报“所有测试通过”，也不要把source、native、visual、history和capacity都塞进一个passed字段。

修改数据的PR须提供ID与保护内容差异；修改渲染的PR须提供固定镜头及边缘／LOD对照；修改资源生命周期的PR须提供真实引用释放与重载证据。

## 8. Q1 最终报告的阅读顺序

先看版本与实际分辨率，再看正确性失败和未执行项，再看视觉审阅，再看真实资源预算与帧时，最后才看通过项总数。原始记录应能重新生成汇总，不能只保留一页绿色结论。

正常profile必须通过。更大探索profile允许失败，但保留其实际数量、可见量、资源字节和瓶颈；不把测试档位从报告中删除，也不能把阈值改到刚好通过后仍称为原预算。
